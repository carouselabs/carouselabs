# Carousel Labs audit and verification - final local checks on 4 October 2026

Status: local implementation and verification completed; release remains blocked by the findings below. Local hardening is implemented on branch `audit/reliability-security-2026-09-28`; no production deployment, live data/access changes, paid generations, email deliveries or credential rotations were performed. Existing user changes were preserved, including extension branding/streaming work and authentication diagnostics. Do not attribute the entire working-tree diff to this audit. This is not a claim of production readiness, complete ASVS compliance, or freedom from vulnerabilities.

## Scope and architecture

- Next.js App Router/React 19/TypeScript web frontend and route-handler backend; Tailwind 4. Next.js moved from 16.2.7 to 16.3.7 with compatible lockfile updates.
- Prisma 5 with PostgreSQL/Supabase connection configuration; Clerk 7 for sessions, verified identities and webhooks. Admin authorization uses the configured verified email; interns use invited identities. Browser extension clients use separate bearer credentials.
- Cloudflare R2 stores images at permanent public URLs. Anthropic generates text/prompts and OpenAI generates images. Redis/Upstash provides distributed limits and image-generation locks. Lemon Squeezy handles web plans, extension subscriptions and top-ups. Resend handles email. LinkedIn OAuth and publishing are implemented; other social platforms have connection/availability gates.
- Vercel cron routes perform publishing, renewal notifications, intern summaries, scheduled emails, email sequences and history cleanup. BullMQ is installed but no working queue worker was found in the workers directory. Do not assume queued AI jobs are durable.
- Separate Vite/React 18 Engage extension in `browser-extension-comment/`; another ideas extension is present. Root unit/browser checks were added; the existing Engage unit suite was reused.
- Reviewed journeys: public landing/legal/tool pages; idea-to-caption/image/carousel editing, saving/reopening and exports; custom posts, bulk imports and scheduling; account/admin/intern boundaries; credits, checkout and webhooks. Live authenticated UI and provider journeys remain unverified.

Trust boundaries include Clerk claims into database identities; client IDs into owner-scoped posts/media; untrusted model output into editable content; source URLs into outbound server requests; checkout metadata/webhooks into subscription and credit writes; extension bearer tokens into private APIs; and cron credentials into provider publication. Server checks, not hidden controls, enforce the reviewed boundaries.

Repository instructions and installed Next.js guides were read before changes. Package/lock files, environment names, Prisma schema/manual SQL, Vercel cron config and existing tests were inspected. The priority was identity/SSRF/payment correctness, then draft loss, bulk-import atomicity and duplicate publication, then measured public loading/accessibility, followed by regression checks and documentation.

A later browser run passed 8/9 and exposed a real first-upload canvas initialization race (blank image/disabled Undo). It was fixed by handing decoded pixels to a layout effect after the canvas commit, with replacement/unmount cancellation and regression tests. PNG encoding was moved to a worker after measuring a 1,039 ms main-thread stall.

Final aggregate `npm run check` completed with 247 tests, no type errors and 16 lint warnings. The production build completed (32.4 s compile, 19.1 s TypeScript, 153 static pages); these are check durations, not comparative performance benchmarks.

The initial sandbox build could not read a parent directory. Production builds passed after isolating the project root/permitted execution. The first browser baseline at 127.0.0.1 was invalid because Clerk rewrote to localhost and produced redirect/proxy errors; its results were discarded. Comparable measurements use localhost. Browser automation used installed Playwright because the in-app browser runtime was unavailable. No test assertions/security checks were disabled to make checks pass. Generated output directories were excluded from source linting.

Unit tests mock Prisma, Clerk, Redis and paid/external services; they verify request/transaction decisions and failure handling, not actual PostgreSQL isolation or provider compatibility. Security webhook tests also use the installed Svix verifier with a local test signature. Actual live accounts A/B were unavailable. Public browser tests cover Chromium at desktop 1440x900, mobile 390x844 and tablet 768x1024: navigation/keyboard access, overflow, headers/CSRF/private cache, bad file recovery, image drawing/undo, decoded header/footer logos, and PNG/WebP download; PNG is checked for indexed color and decoded dimensions. Mobile uses a viewport simulation, not physical hardware. Firefox/WebKit were not run.

## Security findings and unresolved work

Severity is a qualitative prioritization, not a CVSS assessment. [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) informed the reviewed boundaries; this is not a complete ASVS assessment.

| Severity | Evidence | Status |
| --- | --- | --- |
| Critical dependency advisory | Baseline Next 16.2.7; upstream [Windows path traversal/RCE advisory](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36), applicability depends on deployment | Updated to 16.3.7; original findings cleared; 4 Oct scan reports a new glob-tooling advisory, documented below. Hosting OS/runtime configuration still unverified. |
| High advisory: build/lint dependency denial of service | Newly reported [braces advisory](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm), affected through glob tooling | OPEN: no patched version published at 4 Oct verification. 8 root and 5 extension audit entries describe one underlying advisory. No request-input path or traced production-server inclusion identified; this is bounded evidence, not proof of no exposure. Audit CI gates remain failing. |
| High: account binding / privilege | Email reassignment and stale identity paths in auth/admin/intern bootstrap | Fixed locally; mocked identity/race regressions pass. Live two-account and dashboard checks outstanding. |
| High: SSRF | User source URLs and redirects reach privileged server fetches | Shared DNS-pinned bounded transport implemented/tested with mocks. No live network penetration testing. |
| High: payment/credit integrity | Client checkout metadata, concurrent debit/refund pools, webhook replay/order | Signed checkout, exact pool accounting and transactional event processing implemented; provider sandbox and real database concurrency still required. |
| High if media is private | `lib/r2.ts` returns public permanent R2 URLs, bypassing an authenticated proxy | OPEN. Anyone obtaining a URL can read the object. Private-object delivery and a reviewed migration/access policy are required if drafts are promised private. No bucket changes made. |
| High reliability: crash recovery | Refund receipts exist only in request memory; process death between debit, AI/storage and persistence | OPEN. Add a durable operation/credit ledger and reconciliation workflow before claiming crash-safe accounting. Retries after uncertain paid outcomes must not blindly charge again. |
| High reliability: duplicate publication | Timeout/crash can occur after external publication but before local confirmation | Automatic retry now quarantined; manual LinkedIn reconciliation required. Direct interactive publication has no durable provider idempotency guarantee. |
| Medium: browser/input/resource protection | Cross-site writes, API caches, contact limits and image transport | Reviewed controls implemented. CSP only limits base/object/frame; full script/connect policy remains unverified with Clerk/checkout. Other endpoints are not proven uniformly rate/size bounded. |
| Medium: editor data loss | Overlapping saves, stale browser recovery, revision conflicts, changed images/slides | Local save sequencing/ownership/recovery fixes and regression tests; authenticated end-to-end recovery/export still requires staging. |
| Low: privacy diagnostics | Raw error/provider values in reviewed auth/storage/proxy/contact paths | Redacted reviewed locations. Scan is exact local-secret comparison, not history/unknown-secret/log discovery. No rotation performed or exposure revocation claimed. |

Additional limits: bulk-import retries after ambiguous commits still lack batch idempotency and pre-uploaded unused objects can remain; document parsing/decompression and image pixel expansion need resource profiling; queue timezones/DST and concurrent manual queue-slot selection need real database tests; not every route/query/index was profiled; invitation/signup email/referral side effects have no durable outbox; some email/provider paths lack a route-specific deadline. Leave and recurring-slot tests are mocked, not proof of actual isolation under deployed pooler settings. Password reset/session expiry/logout and provider dashboard policies are managed partly by Clerk and remain unverified. User-added extension streaming changes are preserved; this audit does not certify every new extension interaction. Accessibility checks were practical keyboard/layout/reduced-motion checks, not a complete contrast/screen-reader audit.

## Release, deployment and rollback

**Release blockers:** the dependency audit CI gates fail on an unresolved high advisory; obtain a compatible upstream fix and rerun the gates (do not force-downgrade Next or disable checks). Complete staging checks of identity/ownership, payment/webhook behavior, actual persistence/concurrency and saved-image reopen/export; decide/resolve private-media access; implement or explicitly scope durable paid-operation recovery. Do not mark the application production-ready on the strength of mocked tests and public page checks.

1. Review the changes as focused commits; separate existing user extension work. Use an isolated staging database, Clerk A/B accounts, Redis, R2 bucket, Lemon Squeezy test mode and authorized LinkedIn test account. No migration was introduced by this audit. Existing manual SQL/schema compatibility must be verified by the database owner; do not run destructive resets or seeds.
2. Install with `npm ci`, generate Prisma, run the documented checks, then build with deployment environment names from `.env.example`. Match public checkout URLs and configured variant IDs. Keep API/webhook/cron secrets server-side. Configure exact LinkedIn callback and Clerk allowed origins. Require Redis: guarded routes fail closed on outage.
3. Coordinate signed-checkout rollout. Old unsigned checkout links/unfinished purchases may fail new identity validation; regenerate links and reconcile legitimate historical purchases through an approved process. Do not restore email-only matching. Verify webhook signature, duplicate delivery, delayed initial subscription, failed payment, renewal, cancellation and old invoice replay against the provider sandbox.
4. In staging, User A must not read/write/export/delete User B resources or call admin operations. Exercise expiry/logout/suspension, multi-tab save conflicts, refresh recovery, create response loss, image/carousel regenerate-save-reopen, scheduling and export dimensions/content. Test simultaneous debits/invites/leave/recurring reservations against PostgreSQL, duplicate cron ticks and provider timeout after acceptance. Never auto-republish an uncertain job; inspect LinkedIn before confirming retry.
5. Validate browser headers/Clerk checkout/OAuth and extension bearer access behind the real host. Check API no-store and private object delivery, logs without private payloads, measured mobile UI with actual services, and hosting cron duration/secret settings. Public APIs returning private data must remain uncached. CI has been prepared but not executed in GitHub by this audit.
6. Production deployment, live access-policy changes, credential rotation and any cost-incurring tests require the user's separate authorization. No such action was performed. Post-deployment, use approved test data for smoke checks and monitor save conflicts, webhook 4xx/5xx, credit reconciliation and unknown-publication jobs.

Rollback: redeploy the previous reviewed application artifact/lockfile or revert only the audit commits after they have been isolated. There is no audit schema rollback. Do not reset the working tree or overwrite unrelated user work. A code rollback does not reverse provider charges/publications; preserve processed-webhook records and balances, and reconcile uncertain operations before replaying them. Restoring an old release reintroduces its security weaknesses, so prefer a targeted forward fix. Bucket privacy or future ledger migrations need their own separately approved migration/rollback plans.
